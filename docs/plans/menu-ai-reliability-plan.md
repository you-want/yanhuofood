# 菜单 AI 生成稳定性与准确性改造计划

> 状态：已完成
> 创建日期：2026-07-17
> 完成日期：2026-07-18
> 目标路由：`/menus`

## 1. 目标

1. 用户在菜单页选择的日期、周期、餐次、人数、菜品数、预算、健康目标、烹饪时间、忌口、清真、特殊人群和场景参数，必须经过同一套 schema 规范化后准确传入 AI。
2. AI 输出必须是结构化 JSON，并经过 Zod、日期/餐次数量和业务硬约束校验。
3. 长周期生成采用“提纲优先、按天补齐、失败日局部重试”，避免单次长请求失败后全部丢失。
4. AI、数据库或网络失败时保留已完成内容，明确区分 AI 菜单、部分菜单和通用样例。
5. 页面与服务端保持模块化：表单契约、请求解析、偏好合并、prompt、输出校验和 UI 状态分别负责。

## 2. 已发现风险

- 数字输入只依赖 HTML `min/max`，可能把 `0`、空值或超范围值传给 API。
- 请求字段为可选时，直接对象展开会让 `undefined` 覆盖已保存偏好。
- prompt 虽包含主要参数，但缺少一个可审计的“最终参数快照”。
- 输出 schema 校验后仍需要检查忌口、清真等业务硬约束。
- 同步生成超时后直接使用样例，样例不一定满足用户硬约束。
- 部分查询未区分“接口失败”和“确实无数据”。
- 部分 E2E 在关键按钮不存在时直接跳过，可能产生假通过。

## 3. 实施阶段

### Phase A：统一输入契约（已完成）

- [x] 建立菜单生成参数规范化模块。
- [x] 前端提交前使用同一 schema 校验。
- [x] 服务端只使用解析后的规范化参数。
- [x] 合并历史偏好时忽略 `undefined`，保证本次显式参数优先。
- [x] 在生成日志中记录不含密钥的最终参数快照。

验收：非法值不能提交；同一请求在同步和异步链路得到相同最终参数。

### Phase B：输出准确性（已完成）

- [x] prompt 明确标注硬约束、软偏好和完整参数快照。
- [x] Zod 校验日期、餐次、菜品结构。
- [x] 生成后运行忌口、清真和饮食限制检查。
- [x] 硬约束冲突时局部重试，不直接发布冲突结果。

验收：含明确忌口或清真冲突的 AI 结果不能静默成为可采购菜单。

### Phase C：稳定性与恢复（已完成）

- [x] 提纲和单日详情采用独立超时。
- [x] 仅对超时、429、5xx、网络错误和可修复 JSON 错误重试。
- [x] 单日失败保留提纲和已完成日期。
- [x] 任务刷新恢复、失效清理和取消流程完整。
- [x] 样例菜单有醒目标识，并限制直接进入采购。

验收：某一天失败不会丢失整周；失效任务不会无限轮询。

### Phase D：UI 与测试（已完成）

- [x] 抽取菜单生成表单/错误提示组件。
- [x] 显示字段级错误、加载错误和重试操作。
- [x] 移除 E2E 的静默跳过。
- [x] 增加参数传递、边界值、硬约束、超时和恢复测试。
- [x] 运行 `pnpm lint`、`pnpm build`、桌面和移动 E2E。

## 4. 参数优先级

最终传给 AI 的参数按以下优先级解析：

1. 本次菜单页显式选择；
2. 已保存偏好；
3. 产品默认值。

数组字段会去空、去重；字符串会 trim；数字必须在允许范围内。浏览器模型配置只随本次请求发送，不写入 Supabase，也不写入任务 request 记录中的密钥字段。

## 5. 硬约束与软偏好

硬约束：日期数量、餐次数量、每餐菜品数、忌口、清真、特殊人群安全要求。
软偏好：菜系、预算、烹饪时间、健康目标、菜品多样性、反馈偏好。

硬约束失败必须修复、局部重试或明确标记未完成；软偏好允许生成 warning。

## 6. 完成标准

- 首次状态反馈小于 1 秒。
- 正常情况下优先展示菜单提纲。
- 参数契约前后端一致，并有测试证明。
- 输出全部经过 Zod 与业务约束校验。
- AI 样例与真实生成来源清晰可见。
- `lint`、`build`、桌面及移动核心 E2E 全部通过。

## 7. 实施结果

- 统一请求契约已落在 `lib/domain/menu-generation-request.ts` 和 `lib/schemas/menu.ts`，同步、异步生成链路共用规范化结果。
- 渐进式生成支持提纲优先、按天补齐、局部修复、可重试错误分类、任务取消和陈旧任务清理。
- 菜单页已拆分生成表单、结果提示和历史菜单组件；样例菜单在菜单页和采购页均有明确限制。
- E2E 验收期间修复了同周期本地新菜单被服务端旧菜单覆盖、采购状态等待慢速服务端后才恢复、连续快速操作覆盖前一次状态三个问题。
- 历史菜单查询在 Supabase 网络不可达时会进入本地只读降级，保留浏览器菜单并显示可重试提示；权限、SQL 和 schema 错误仍按真实失败处理。
- 偏好和菜品反馈在 Supabase 网络不可达时同样回落到浏览器存储；服务端数据库请求默认 3 秒超时，埋点写入最多阻塞 300ms。
- 食谱库会区分加载失败与空数据，新增、编辑和删除失败不会再触发成功状态或关闭表单。
- 2026-07-18 最终验证：`pnpm lint` 通过，`pnpm build` 通过，Playwright 桌面 Chromium 与移动 iPhone 12 项目共 54 项全部通过；真实 Supabase 停机降级耗时约 3.0 秒。
