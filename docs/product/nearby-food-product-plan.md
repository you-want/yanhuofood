# “附近吃什么”产品与技术实施方案

> 文档状态：MVP 已实现，支持站点公共 Key、用户自带 Key 与公共 Key 每日额度保护
> 创建日期：2026-07-22
> 适用项目：烟火食间（yanhuofood）

## 1. 背景与产品目标

很多用户处于上班状态，工作日通常只能选择公司食堂、公司附近餐馆或外卖。当前烟火食间擅长家庭菜单、即时做饭推荐和饮食偏好管理，但还缺少“结合真实地理位置，从附近真实商家中完成一餐决策”的能力。

本功能建议定义为独立产品模块：

> **附近吃什么：基于用户位置、预算、时间、口味、健康目标和最近选择，从附近真实餐馆中筛选并推荐今天的一餐。**

核心目标不是简单展示一个地图列表，而是缩短用户从“我不知道吃什么”到“就吃这家”的决策路径。

建议在导航中使用名称：

- 附近吃什么

可选营销或页面副标题：

- 上班吃什么
- 周边觅食
- 午饭决策器
- 今日外食

## 2. 核心结论与实现边界

需要先区分两个数据问题。

### 2.1 附近有哪些餐馆

可以使用高德、百度或腾讯位置服务的地图 POI API，根据用户经纬度、半径、关键词和餐饮分类检索附近门店。

这是第一阶段可以稳定实现的能力。

### 2.2 哪些餐馆现在可以点外卖

真实外卖推荐还依赖：

- 当前用户地址是否在配送范围内
- 实时配送费
- 起送价
- 预计送达时间
- 菜品列表和库存
- 优惠券和会员价格
- 商户当前营业状态

地图 POI API 通常不能完整提供这些信息。这类数据需要美团、淘宝闪购等平台的官方合作能力，不能把爬取外卖平台页面作为正式生产系统的核心数据源。

因此，推荐整体路线为：

```text
第一阶段：地图 POI → 附近餐馆发现和选择
第二阶段：智能筛选 → 自然语言、偏好和随机推荐
第三阶段：工作餐计划 → 五天不重样、预算和健康轮换
第四阶段：官方合作 → 真实外卖菜单、配送和下单
```

第一版产品只承诺：

> 根据用户位置，找到附近真实餐馆，并结合距离、预算、口味和历史偏好帮助用户选择。

第一版不承诺：

> 系统知道所有餐馆的真实外卖状态、优惠、配送费和送达时间。

## 3. 产品场景

### 3.1 一键帮我选

用户没有明确想法时，点击：

- 帮我选一家
- 换一家
- 给我三个选择

系统根据以下条件推荐：

- 距离
- 用户口味
- 预算
- 餐厅评分
- 当前是否营业
- 最近是否选择过
- 用户喜欢或拉黑的门店
- 用户的健康方向

### 3.2 按条件找餐馆

用户可以选择快捷筛选，也可以输入自然语言。

示例：

> 想吃清淡一点的，30 元以内，步行十分钟，不要面。

系统先将自然语言转换成结构化条件：

```json
{
  "max_price": 30,
  "max_walk_minutes": 10,
  "flavors": ["清淡"],
  "excluded_categories": ["面食"]
}
```

然后筛选真实 POI，不允许让大模型凭空生成餐厅。

### 3.3 工作日午餐规划

用户可以提出：

> 给我安排本周五天的工作午餐，每天不重样，平均不超过 35 元。

系统先搜索公司附近的真实餐馆，再进行分配：

| 日期 | 推荐方向 | 示例结果 |
| --- | --- | --- |
| 周一 | 米饭套餐 | 中式快餐 |
| 周二 | 轻食 | 沙拉或谷物碗 |
| 周三 | 粉面 | 米粉或汤面 |
| 周四 | 高蛋白 | 鸡肉饭或牛肉饭 |
| 周五 | 自由探索 | 最近没有吃过的新类型 |

这一能力可以在后续与当前项目已有的 `work_takeout` 菜单场景结合。

### 3.4 外卖平台辅助选择

第一阶段提供：

- 餐馆名称
- 距离
- 地址
- 餐饮分类
- 部分门店的评分
- 部分门店的均价
- 部分门店的营业状态
- 复制店名
- 地图导航
- 通过官方支持的链接打开外部平台搜索

第一阶段不应直接显示未经数据源确认的：

- 可配送
- 配送费
- 起送价
- 实时优惠
- 预计送达时间
- 菜品库存

## 4. 数据来源方案

### 4.1 推荐方案：地图 POI API

推荐 MVP 优先使用高德地图搜索 POI 2.0，通过 WebService API 在服务端检索附近餐饮门店。

Key 支持双模式：

- 站点可以在服务端环境变量中配置公共 Key，作为所有用户的默认能力。
- 站点不配置公共 Key 时，用户可以在 `/nearby` 页面填写自己的“Web 服务”Key。
- 用户 Key 只保存在当前浏览器，发起地图请求时临时发送给当前站点后端；服务端调用高德后不保存。
- 用户本地 Key 存在时优先使用，服务端公共 Key 作为回退。
- 服务端公共 Key 可配置每日总调用单位上限；用户本地 Key 不占用站点额度。

输入通常包括：

```text
当前位置：经纬度
搜索范围：例如 1500 米
地点类型：餐饮服务
关键词：例如轻食、快餐、米饭
分页：页码和每页数量
```

标准化后可能得到：

```json
{
  "provider": "amap",
  "provider_place_id": "B0XXXX",
  "name": "某某轻食",
  "address": "某某路 100 号",
  "location": {
    "latitude": 31.23,
    "longitude": 121.47
  },
  "distance_m": 680,
  "category_name": "餐饮服务;快餐厅",
  "rating": 4.6,
  "average_cost": 32,
  "opening_hours": "10:00-21:00"
}
```

注意：实际响应字段以服务商接口为准。不能假设所有门店都有评分、均价和营业时间。

地图 API 适合解决：

- 附近有哪些餐馆
- 餐馆名称和地址
- 经纬度和直线距离
- 餐饮分类
- 商圈
- 部分评分和均价
- 部分营业时间
- 地图展示和导航

地图 API 不能可靠解决：

- 当前地址是否可配送
- 实时外卖菜单
- 菜品库存
- 实时配送费
- 实时优惠
- 实时送达时间
- 菜品级营养
- 菜品是否符合过敏原要求

### 4.2 服务商选择

第一推荐：高德地图。

理由：

- 中国大陆 POI 场景适配较好
- 周边搜索接口清晰
- 餐饮分类较丰富
- Web、WebService 和路线规划能力相对完整
- 后续可以接地图展示和步行路线

备选：

- 百度地图地点检索
- 腾讯位置服务地点搜索

不要在第一阶段同时接入多个服务商。代码层面应使用适配器隔离具体供应商：

```ts
interface PlaceProvider {
  searchNearby(input: NearbySearchInput): Promise<NearbyPlace[]>;
  resolveAddress?(address: string): Promise<GeoPoint>;
}
```

第一阶段只实现：

```ts
class AmapPlaceProvider implements PlaceProvider
```

后续切换服务商时，不需要修改页面和推荐算法。

### 4.3 外卖平台官方合作

真实外卖能力应走官方接入或商务合作，可能包括：

- 可配送门店
- 菜品列表
- 菜品价格
- 起送价
- 配送费
- 预计送达时间
- 优惠活动
- 下单跳转
- 订单状态

这类开放能力通常面向注册开发者、商家、品牌或生态合作方，需要创建应用、申请权限并完成业务接入。它不应成为 MVP 的前置依赖。

### 4.4 不推荐：爬取外卖平台

即使某一时期技术上可以抓取，也会遇到：

- 登录状态和验证码
- 地址绑定
- 动态签名
- 设备指纹和反爬风控
- 页面结构频繁变化
- 不同配送地址看到的内容不同
- 用户会员、优惠券和历史行为导致结果个性化
- 平台服务条款和数据授权风险

原则：

> 不把爬虫接入正式产品主链路，不依赖抓取结果保障核心功能，也不通过抓取批量构建自己的第三方 POI 或外卖数据库。

### 4.5 地图数据授权注意事项

上线前必须确认：

- 企业开发者认证
- Key 类型和使用范围
- 商业使用许可
- 数据展示规则
- 数据缓存和落库限制
- 地图 Logo、版权标识和来源标注
- 图片、电话、评分等扩展数据的展示权限
- QPS、日调用量和付费配额

流量调用价格通常不是最大风险，商业授权和数据使用边界更重要。

## 5. 页面与交互设计

建议新增独立路由：

```text
/nearby
```

不建议第一阶段直接塞进菜单生成页，避免把“在家做饭”和“附近外食”两种实体和交互混在一起。

### 5.1 桌面端布局

遵循项目宽屏优先和 `max-w-[1600px]` 原则：

```text
┌──────────────────────────────────────────────────────────────┐
│ 位置：上海市某某大厦                  重新定位 / 修改地址       │
├──────────────┬──────────────────────────┬────────────────────┤
│ 筛选条件      │ 推荐结果列表              │ 地图                │
│              │                          │                    │
│ 距离          │ 餐厅卡片                  │ POI 标记            │
│ 预算          │ 餐厅卡片                  │                    │
│ 菜系          │ 餐厅卡片                  │                    │
│ 健康目标      │ 餐厅卡片                  │                    │
│ 排除项        │                          │                    │
│              │                          │                    │
│ 帮我选一家    │                          │                    │
└──────────────┴──────────────────────────┴────────────────────┘
```

第一版可以先做列表模式，不立即接入地图 JS SDK：

- 左侧筛选栏
- 右侧结果列表
- 餐厅卡片中展示距离和地址

这样可以减少地图加载、客户端 Key、地图授权和移动端地图交互的复杂度。

### 5.2 移动端布局

- 顶部位置栏
- 条件快捷标签
- 列表/地图切换
- 底部固定“帮我选一家”按钮
- 高级筛选放进抽屉或弹窗
- 餐厅卡片操作按钮避免换行

### 5.3 入口关系

当前 `/today` 更偏向在家做饭和现有食材。可以在后续为今日决策增加入口：

```text
今天准备怎么吃？

[在家做] [附近吃] [点外卖]
```

路由建议：

- 在家做 → `/today`
- 附近吃 → `/nearby`
- 点外卖 → `/nearby?mode=delivery`

在没有平台真实配送数据时，`delivery` 模式应明确提示：

> 最终配送范围、价格和送达时间以外部平台为准。

## 6. 筛选条件

### 6.1 快捷条件

第一屏只展示最常用条件：

- 500 米内
- 步行 10 分钟
- 30 元以内
- 清淡一点
- 高蛋白倾向
- 少油少盐
- 不吃辣
- 快餐
- 米饭
- 粉面
- 轻食
- 当前营业

### 6.2 距离

- 500 米
- 1 公里
- 1.5 公里
- 3 公里
- 自定义

### 6.3 时间

- 步行 5 分钟
- 步行 10 分钟
- 步行 15 分钟
- 预计 30 分钟内吃完

MVP 可以使用直线距离估算步行时间：

```text
估算步行时间 = 直线距离 / 70 米每分钟 × 绕路系数 1.25
```

该结果必须标记为估算。正式版只对评分靠前的少数候选调用步行路线 API，控制额外调用量。

### 6.4 预算

- 20 元以内
- 20～30 元
- 30～50 元
- 50 元以上

如果数据源没有均价：

- 不直接排除
- 展示“价格未知”
- 降低数据可信度分
- 不允许 AI 猜测价格

### 6.5 口味和菜系

- 中式快餐
- 川湘菜
- 粤菜
- 东北菜
- 西北菜
- 日料
- 韩餐
- 西餐
- 轻食
- 粉面
- 饺子馄饨
- 汉堡炸鸡
- 咖啡简餐

### 6.6 健康倾向

- 热量适中
- 高蛋白
- 蔬菜多
- 少油
- 少盐
- 少糖
- 不要油炸

只有 POI、没有菜单时，不能准确判断一家店是否高蛋白、低脂或少盐。健康条件需要分级：

1. 餐厅类型推断：轻食、沙拉、汤饭等只作为弱信号。
2. 菜品级判断：获得菜单或用户选择具体菜品后才能给出更可信的判断。

页面提示：

> 根据餐厅类型推测，具体请以实际菜品为准。

### 6.7 忌口、过敏和特殊饮食

- 明确的拉黑餐厅可以硬过滤。
- 仅凭餐厅名称或分类，不能保证清真、无麸质或不含某种过敏原。
- 如果缺少菜单和商家确认，只能展示“需要向商家确认”。
- 不允许 AI 将模糊推断包装成确定事实。

## 7. 推荐算法

“随机推荐”不能做成完全随机，否则容易抽到很远、低分、超预算、不营业或用户刚吃过的门店。

推荐使用：

> **硬性过滤 + 综合评分 + 加权随机。**

### 7.1 硬性过滤

先排除：

- 超出最大距离
- 明确已关闭或不营业
- 明确不符合餐饮分类
- 用户明确拉黑
- 最近选择且用户要求避免重复
- 在价格可靠时明确超预算

未知信息不能被当成不符合。例如价格未知时，不能直接判断为超预算。

### 7.2 综合评分

MVP 建议权重：

```text
综合得分 =
  距离匹配       25%
+ 菜系口味匹配   20%
+ 预算匹配       15%
+ 评分质量       15%
+ 营业状态       10%
+ 新鲜度         10%
+ 数据可信度      5%
```

只有 POI 数据时，健康目标不宜占太高权重。获得菜品菜单后再增加健康匹配权重。

### 7.3 加权随机

不是永远返回第一名，而是从高分候选中按权重抽取。

模式建议：

#### 稳妥模式

- 从前 5 名中抽取
- 更关注距离、评分和预算

#### 平衡模式

- 从前 10～15 名中抽取
- 默认模式

#### 惊喜模式

- 从前 20～30 名中抽取
- 提高没吃过、新菜系和新门店的概率
- 仍然必须满足硬性条件

可以用温度参数控制随机性：

```text
稳妥模式：temperature = 0.3
平衡模式：temperature = 0.7
惊喜模式：temperature = 1.2
```

抽样概率可以使用：

```text
P(place_i) ∝ exp(score_i / temperature)
```

### 7.4 避免重复

支持：

- 最近 7 天不重复
- 最近 14 天不重复
- 最近 30 天降低重复概率

如果附近候选不足，不应完全无结果，而应：

1. 优先放宽“重复”软条件
2. 保留距离、忌口和拉黑等硬条件
3. 明确告诉用户放宽了什么条件

## 8. AI 的职责边界

### 8.1 AI 应该做

#### 自然语言转筛选条件

用户输入：

> 公司附近吃个便宜的，不要太辣，最好有肉有菜。

结构化输出：

```json
{
  "max_distance_m": 1500,
  "budget_max": 35,
  "spicy_level": "low",
  "preferences": ["荤素搭配"],
  "excluded_categories": []
}
```

输出必须通过 Zod 校验。

#### 解释推荐原因

AI 只能基于真实候选字段解释：

```json
{
  "name": "某某鸡肉饭",
  "distance_m": 560,
  "category": "中式快餐",
  "average_cost": 28,
  "rating": 4.5
}
```

允许的解释：

> 距离约 560 米，均价在你的 30 元预算附近，而且属于你偏好的中式快餐。

#### 差异化三个候选

- 最近的一家
- 性价比最高的一家
- 今天换口味的一家

### 8.2 AI 不应该做

- 凭空生成不存在的餐厅
- 猜测配送费和送达时间
- 猜测优惠和起送价
- 猜测营业状态
- 猜测菜品库存
- 根据餐厅名称保证无过敏原
- 将用户精确经纬度发送给不必要的模型
- 绕过确定性硬条件

正确流程：

```text
位置 API
  ↓
真实 POI 候选
  ↓
确定性筛选
  ↓
确定性评分
  ↓
加权随机
  ↓
AI 负责意图解析和结果解释
```

错误流程：

```text
把位置告诉 AI
  ↓
让 AI 猜附近有什么餐厅
```

## 9. 与现有项目的结合

### 9.1 复用 `work_takeout`

当前类型中已经存在：

```ts
type MenuScenario =
  | "daily_home"
  | "travel"
  | "work_takeout"
  | "batch_cooking"
  | "festival";
```

后续可以支持：

> 根据公司附近真实餐厅生成五天工作午餐计划。

第一阶段不要直接把 POI 当作现有 `Dish` 或 `Meal` 写入菜单结构，原因包括：

- 餐厅与菜品不是同一类实体
- 会增加旧菜单兼容复杂度
- 地图数据可能存在授权和缓存限制
- 外部餐厅可能下线、改名或改变营业状态

## 14. 定位流程与坐标处理

### 14.1 定位流程

1. 用户主动点击“使用当前位置”
2. 浏览器请求定位权限
3. 获取浏览器 GPS/WGS84 坐标和定位精度
4. Provider 将 GPS 坐标转换为高德坐标，并调用逆地理编码解析道路、门牌或可读地址
5. 页面展示详细地址、坐标系、经纬度和定位精度，供用户核对真实位置
6. 使用转换后的高德坐标搜索附近门店，避免重复转换和坐标偏差
7. 定位精度太差时提示重新定位或手动输入公司/园区地址
8. 用户拒绝定位时提供地址输入
9. 逆地理编码失败时保留原始 GPS 坐标继续搜索，并明确提示详细地址未能解析

不要在页面首次加载时直接弹出定位授权。

### 14.2 定位失败降级

提供：

- 输入公司地址
- 选择常用地点
- 在地图上选点
- 使用上次保存在本浏览器的公司位置

### 14.3 坐标系

浏览器、地图服务商和地图 SDK 可能使用不同坐标体系。Provider 层应负责：

- 明确输入坐标类型
- 必要时进行坐标转换
- 保证搜索结果距离与地图标记一致
- 逆地理编码结果与最终搜索坐标使用同一高德坐标，页面同时保留浏览器返回的定位精度
- 编写固定坐标测试用例

不能在业务页面散落坐标转换逻辑。

## 15. 位置隐私与安全

精确位置属于高敏感数据场景，遵循：

- 明确目的
- 用户主动授权
- 最小必要
- 最短保存时间
- 可撤销
- 不用于与功能无关的画像

MVP 建议：

- 不在 Supabase 保存实时经纬度
- 不在服务端普通日志中记录原始经纬度
- 不把经纬度发送给 AI
- 不记录用户每次搜索形成位置轨迹
- 公司位置默认只保存在当前浏览器
- 只在当前请求生命周期中使用位置
- 分析埋点只记录模糊区域或城市级别
- 错误日志主动过滤位置字段
- 用户高德 Key 只保存在当前浏览器的 `yanhuofood.localAmapConfig`
- 用户 Key 不写入 Supabase、分析事件或普通日志
- 页面明确说明 localStorage 不适合公共电脑，并提供一键清除
- 服务端只在单次地址解析或附近搜索请求中使用用户 Key

如果以后需要跨设备同步公司位置，应增加：

- 明确开关
- 用途说明
- 单独同意
- 删除功能
- 保存期限
- 数据导出或清理机制

### 16.3 第三方数据缓存

## 17. 异常与降级

### 17.1 用户拒绝定位

显示：

- 输入公司地址
- 使用常用位置
- 地图选点

### 17.2 地图服务不可用

显示：

- 重新搜索
- 修改搜索半径
- 使用简化决策器，例如米饭、面食、轻食三选一

### 17.3 搜不到结果

自动尝试：

1. 半径从 500 米扩大到 1 公里
2. 从 1 公里扩大到 2 公里
3. 移除过于严格的软条件
4. 告诉用户放宽了哪些条件

不能静默放宽：

- 忌口
- 过敏
- 明确拉黑
- 明确特殊饮食要求

### 17.4 数据缺失

- 评分缺失 → “评分暂无”
- 价格缺失 → “价格未知”
- 营业时间缺失 → “营业状态需确认”
- 外卖信息缺失 → “请在外部平台确认配送”

不能让 AI 补齐未知字段。

### 17.5 API 防滥用

- 限制单 IP 和单 client_id 请求频率
- 限制半径和分页
- 限制关键词长度
- 服务端公共地图 Key 可选；用户可以临时提供本浏览器 Key
- 用户 Key 优先于服务端公共 Key，且不得持久化
- 给第三方请求配置超时
- 统一处理服务商错误码
- 不在错误响应中暴露 Key 或原始上游响应

### 17.6 公共 Key 每日额度保护

站点公共 Key 使用全站共享硬上限，避免匿名用户流量或异常请求产生不可控费用。限制的是高德上游请求单位，而不是页面按钮点击：

| 操作 | 调用单位 |
| --- | ---: |
| 地址解析 | 1 |
| 高德坐标附近搜索 | 1 |
| GPS 坐标附近搜索 | 2（坐标转换 + 搜索） |
| 高德坐标逆地理编码 | 1 |
| GPS 坐标逆地理编码 | 2（坐标转换 + 逆地理编码） |

一次常见的“GPS 定位 → 展示详细地址 → 搜索附近餐馆”流程通常消耗 3 个调用单位。小规模上线建议先设置每天 `150` 个单位，约等于每天 50 次完整流程；后续根据高德控制台实际配额、近 7 天使用量和活跃用户逐步调整。

实现配置：

```bash
AMAP_PUBLIC_DAILY_REQUEST_LIMIT=150
AMAP_PUBLIC_QUOTA_TIME_ZONE=Asia/Shanghai
AMAP_PUBLIC_QUOTA_BUCKET=production
```

实现原则：

- 只限制 `AMAP_WEB_SERVICE_KEY`，用户浏览器自己的 Key 直接绕过。
- 使用 Supabase PostgreSQL RPC 原子增加计数，保证并发请求不能突破硬上限。
- 计数仅保存日期、环境 bucket 和汇总单位，不保存用户 ID、IP、地址、经纬度或 Key。
- production 和 staging 共用 Supabase 时，通过 bucket 隔离额度。
- 配置为 `0` 或不配置时关闭应用侧限额。
- 开启保护后如果数据库、service role key、表或 RPC 不可用，公共 Key 采用 fail-closed：暂停调用并提示用户填写自己的 Key。
- 页面展示剩余额度，并在每次公共地图请求完成后刷新状态；服务端原子计数始终是最终保护边界。

| POI 信息不完整 | 预算、营业状态判断不稳定 | 展示未知状态，增加数据可信度 |
| 外卖信息缺失 | 无法显示配送费和送达时间 | 明确产品边界，后续官方合作 |
| 平台授权限制 | 影响缓存、展示和商业上线 | 阶段 0 先确认许可 |
| 定位被拒绝 | 无法自动搜索 | 地址输入、常用位置、地图选点 |
| 坐标系不一致 | 距离和地图标记错误 | Provider 层统一转换并测试 |
| AI 幻觉 | 产生虚假餐馆信息 | AI 不负责检索，只解释真实候选 |
| 严格筛选无结果 | 用户无法完成决策 | 分级放宽软条件并明确提示 |
| API 被滥用 | 成本和配额异常 | 限流、分页上限、超时和监控 |
| 健康标签不准确 | 误导用户 | POI 阶段只做弱推断并提示确认 |
| 第三方门店变化 | 历史结果失效 | 实时重新查询，不长期复制数据 |

## 22. 推荐实施顺序

```text
真实 POI 搜索
→ 标准化 Provider 层
→ 筛选和可信度
→ 加权随机
→ 用户选择反馈
→ 自然语言输入
→ 地图和步行路线
→ 工作日午餐计划
→ 外卖平台官方合作
```

第一版技术选择：

- 数据源：高德搜索 POI 2.0
- 请求位置：Next.js 服务端 Route Handler
- Key：用户本地 Key 优先，服务端环境变量作为可选公共回退
- 公共 Key 保护：Supabase 原子日计数，默认建议 150 个调用单位/日
- 用户 Key 存储：版本化 localStorage，只随地图请求临时发送，不写入 Supabase
- 前端定位：浏览器 Geolocation API
- 输入输出校验：Zod
- 请求状态：React Query
- 推荐：确定性过滤和评分 + 加权随机
- AI：只做自然语言解析和推荐解释
- 偏好与历史：优先 localStorage
- Supabase：暂不保存精确位置和第三方 POI
- 页面：独立 `/nearby`
- 与菜单集成：阶段 3

预计在地图服务账号、授权和数据质量验证顺利的情况下，一名熟悉当前项目的全栈开发者可以在约两周内完成第一版可用 MVP。
