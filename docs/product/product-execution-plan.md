## 1. 结论先行

烟火食间已经不是一个只有概念的 MVP。当前代码已经具备菜单生成、结构化校验、菜单编辑与保存、历史菜单、营养估算、采购清单、食谱库、本地存储降级和多场景 Prompt。接下来最重要的工作不是再增加旅行、外卖或电商模块，而是解决以下四个产品问题：

1. **首次价值到达太慢**：快捷入口仍会把用户带到参数很多的菜单页，用户没有真正“一键得到结果”。
2. **生成结果可控性不足**：目前可以直接改菜名和热量，但不能低成本替换某一餐，也没有记录“不喜欢”的原因。
3. **采购闭环没有持续状态**：勾选结果只存在页面内，刷新或换设备后无法恢复，也不能排除家中已有食材。
4. **没有产品数据闭环**：已有 AI 生成日志，但缺少用户行为事件，无法判断生成之后是否真的进入采购和复用。

因此，本轮一周冲刺的产品主线应是：

> **让一个家庭做饭者在 3 分钟内得到可接受的菜单，5 分钟内完成调整，并能拿着一份准确、可持续勾选的清单去采购；下周可以基于上周反馈快速再生成。**

## 2. 对早期产品想法的再判断

### 2.1 判断正确的部分

- “吃什么、怎么买、怎么做”是正确的核心闭环。
- 决策效率比“AI 能力丰富”更接近用户价值。
- 首次使用需要示例场景和更好的空状态。
- 模型配置应属于高级设置，普通用户不应先理解供应商、Base URL 和 API Key。
- 移动端采购与厨房查看体验值得重点投入。
- 用户对菜品的实际反馈，是后续个性化的关键数据。

### 2.2 需要调整的部分

- **暂缓生鲜电商接入**：食材还没有稳定标准化，库存、包装、地区和价格也没有数据基础。现在接平台会放大错误，无法证明核心留存。
- **暂缓家庭共享**：在账户、数据归属和长期使用尚未验证前，共享会引入邀请、权限、冲突和通知等额外复杂度。
- **暂缓旅行外食扩展**：Prompt 场景已有第一版，但缺少实时地点和商家数据。它与家庭采购闭环的用户任务不同，不应进入近期主线。
- **不采用“匿名数据换免费”作为近期商业模式**：用户价值感知弱，且会增加隐私说明、授权和数据治理成本。
- **营养展示先提高可信度，不先扩大字段数**：在没有可靠营养数据库前，增加维生素和矿物质只会制造更精细但未必更准确的数字。

## 3. 目标用户与使用场景

### 3.1 唯一首要用户

**每周在家做饭 3 次以上、需要为 1 到 4 人安排餐食的家庭主要做饭者。**

典型特征：

- 每周至少有一次集中想菜单或采购的行为。
- 关心口味、忌口、时间和预算，但不要求医疗级营养方案。
- 最痛苦的不是缺少菜谱，而是组合菜单、减少重复和整理采购清单。
- 会在桌面端规划，也会在手机上采购或做饭。

### 3.2 次要用户

- 有明确减脂、高蛋白或控糖目标的个人做饭者。
- 需要周末集中备菜的上班族。

儿童、老人、孕妇只作为限制条件支持，不把产品定位为专业营养或医疗工具。

### 3.3 核心任务

> 当我准备安排未来几天的家庭餐食时，我希望快速得到符合人数、口味、预算和做饭时间的菜单；不满意时只改少数餐；确认后自动得到采购清单，并让下次规划比这次更省事。

## 4. 产品目标与指标

### 4.1 北极星指标

**每周完成闭环的有效计划数（Weekly Executed Plans）**

一个“有效计划”必须在同一菜单上满足：

1. AI 菜单成功生成或历史菜单被复用；
2. 用户至少查看一次采购清单；
3. 用户完成下列任一执行行为：勾选 3 个食材、导出清单、保存修改后的菜单。

这个指标同时覆盖生成质量和真实执行，避免只追求“生成次数”。

### 4.2 本轮发布目标

开发开始时记录当前基线，核心闭环发布后按 7 天和 14 天两个窗口观察。

| 指标 | 定义 | 发布后 14 天目标 |
| --- | --- | --- |
| 首次生成完成率 | 首次进入菜单页后成功得到非样例菜单的用户 / 首次进入菜单页用户 | >= 55% |
| 技术生成成功率 | AI 成功或修复成功的请求 / 全部生成请求，样例兜底单列 | >= 95% |
| 生成耗时 | 1 天菜单 P95 / 7 天菜单 P95 | <= 20 秒 / <= 45 秒 |
| 菜单接受率 | 生成后未整单重生成，且进入保存或采购的菜单 / 成功生成菜单 | >= 45% |
| 采购清单打开率 | 查看采购清单的成功菜单 / 成功生成菜单 | >= 40% |
| 有效计划率 | 有效计划 / 成功生成菜单 | >= 30% |
| 次周回访率 | 首周产生有效计划且第 7 至 14 天再次规划的用户占比 | >= 20% |
| 样例兜底率 | `source=sample` 的生成 / 全部生成 | <= 5% |

绝对目标用于发现明显问题，产品决策同时看每个版本相对基线的变化，不以小样本的单周波动做结论。

### 4.3 护栏指标

- 每个有效计划的模型成本不得连续两周上升超过 20%。
- 单餐替换不得改动未选择的日期和餐次。
- 忌口、清真和过敏相关约束违反率必须为 0；发现后按 P0 缺陷处理。
- 涉及特殊人群的页面必须持续显示“日常参考，不替代专业建议”。

## 5. 核心产品流程

```text
首页场景模板
    -> 确认少量关键条件
    -> 生成并展示可恢复进度
    -> 接受 / 替换单餐 / 手动修改
    -> 查看菜品做法
    -> 生成采购清单
    -> 排除家中已有 + 持续勾选
    -> 标记喜欢/不喜欢/做过
    -> 下周沿用偏好快速再规划
```

首次用户最多先回答 4 个问题：人数、计划天数、每天餐次、明确忌口。菜系、预算、健康目标和做饭时间使用合理默认值，生成前可展开修改，生成后也能保存为长期偏好。

## 6. 一周 AI 开发路线图

### 阶段 0：建立可测量且可靠的基线（第 1 个工作日）

目标：在改体验前先知道用户卡在哪里，并修复会污染数据的存储问题。

任务：

- 新增白名单式产品事件记录，事件不保存 API Key、完整 Prompt、完整模型输出和自由输入内容。
- 建立基础漏斗看板：进入菜单页 -> 开始生成 -> 生成成功 -> 调整/保存 -> 打开清单 -> 执行动作。
- 为 `preferences` 增加 `client_id` 唯一约束，确认 upsert 不会重复插入。
- 为菜单建立明确的 `client_id + start_date` 唯一策略，避免同周期历史记录重复或查询 `maybeSingle()` 失败。
- 食谱增加数据归属；在引入账户前至少按 `client_id` 隔离，不能继续把所有用户食谱作为全局库读写。
- 建立 30 组固定生成案例，覆盖忌口、人数、周期、餐次、场景和特殊人群；自动校验日期、餐次数、食材完整度和硬性限制。

验收标准：

- 可以按匿名 `client_id` 查看完整核心漏斗，且事件中没有敏感模型配置。
- 同一用户重复保存偏好和同周期菜单不会产生不可控重复记录。
- 两个不同浏览器标识不能互相读取或修改个人食谱。
- 30 组案例可重复执行并输出成功率、兜底率和耗时报告。

### 阶段 1：缩短首次价值到达时间（第 2 个工作日）

目标：用户不理解模型和复杂参数，也能快速得到第一份菜单。

任务：

- 首页增加 3 个真正可执行的场景模板：`三口之家 7 天家常菜`、`一人 5 天省时餐`、`减脂高蛋白 5 天餐`。
- 模板直接预填参数并进入简化确认区；用户确认后一次点击生成，不再重新填写完整表单。
- 菜单页默认只展示关键条件，高级条件放入可展开区域。
- 首页“配置模型”不再作为普通用户主快捷操作；仅在服务器无可用模型时显示阻塞提示和配置入口。
- 菜单生成切换为可恢复的任务状态：刷新或离开后返回，仍能看到最近任务状态和结果。
- 明确区分 AI 结果与样例兜底，样例菜单不能以“生成成功”混入产品指标。
- 完成移动端首次生成流程检查，重点验证输入可读性、按钮换行和生成状态不跳动。

验收标准：

- 新用户从首页到发起生成不超过 2 次主要点击、4 个必填选择。
- 模板生成参数可在提交前查看和修改。
- 生成中刷新页面后可以恢复状态；失败后提供重试和样例查看两个明确动作。
- 首次生成完成率相对阶段 0 基线提升至少 20%。

### 阶段 2：让结果可控、可接受（第 3 个工作日）

目标：用户不满意某一餐时，不需要重新生成整周。

任务：

- 增加“替换这一餐”，支持原因：不爱吃、食材难买、太复杂、太贵、重复、其他。
- 替换请求携带当前菜单摘要和目标餐次，只返回被替换餐，并在服务端校验原菜单其余部分不变。
- 支持“换一道菜”和“替换整餐”两个粒度；多菜家庭餐不应只能整体覆盖。
- 保留手动编辑，但编辑结构化菜品时同步维护食材和营养状态；无法同步时明确标记“需重新计算”，不能保留旧数字造成误导。
- 增加菜品详情抽屉，直接展示已有结构化食材、步骤、耗时、难度和注意事项；外部搜索作为次要入口。
- 生成前进行硬性约束检查，结果中发现忌口或饮食限制冲突时禁止直接进入采购清单。

验收标准：

- 单餐替换成功率 >= 95%，且未选中的餐次 JSON 保持不变。
- 替换后采购清单使用新餐食食材，不残留被替换菜品。
- 结构化菜品详情无需离开站点即可完成一次做饭信息查看。
- 菜单接受率相对上一版本基线提升至少 15%。

### 阶段 3：完成真实采购闭环（第 4 个工作日）

目标：采购清单从一次性展示变成可以实际使用的任务清单。

任务：

- 为每份菜单持久化采购清单状态，刷新后保留已勾选项。
- 增加“家中已有”状态，与“已购买”分开；默认从待采购列表排除，但可以恢复。
- 统一常见单位并标记无法合并的用量，避免把同一食材的 `克`、`个`、`适量`错误相加。
- 支持按日期选择采购范围，例如只买未来 2 天，而不是强制购买整周生鲜。
- 增加平台无关的“复制清单文本”和系统分享能力，保留 CSV、PNG 和打印。
- 优化手机端单手勾选、分类折叠、进度显示和离线/弱网下的本地状态。

验收标准：

- 勾选、家中已有和分类状态刷新后可恢复。
- 修改或替换菜单后，系统展示清单差异并让用户确认更新，不静默清空采购进度。
- 用户可以生成任意连续日期范围的采购清单。
- 采购清单打开率达到 40%，清单打开后的执行动作率达到 60%。

### 阶段 4：形成下周复用与反馈闭环（第 5 个工作日上午）

目标：让第二次规划明显比第一次更省事。

任务：

- 菜品支持“喜欢”“不想再吃”“做过了”三个轻量反馈。
- 将替换原因和菜品反馈存为结构化数据，不保存用户自由文本到模型日志。
- 新增“沿用上周偏好生成下周菜单”，默认保留人数、餐次、预算和时间限制。
- 支持复制整周后调整日期，并提示季节性和重复菜品。
- 生成时优先召回用户喜欢或收藏的食谱，排除“不想再吃”，并限制一周内重复。
- 首页“下一步”根据状态变化：无菜单 -> 生成；有菜单未采购 -> 去清单；本周已执行 -> 规划下周。

验收标准：

- 反馈能实际改变后续生成候选，而不只是被记录。
- 一键生成下周菜单时，长期偏好与上周确认设置一致。
- 次周用户完成新计划所需的参数操作数量比首次减少 50%。
- 次周回访率达到 20%。

### 阶段 5：集成发布与复盘（第 5 个工作日下午，发布后第 14 天完成指标复盘）

目标：根据行为数据决定继续做家庭闭环，还是开始扩展账户、营养或新场景。

任务：

- 按首次模板、计划天数、人数和健康目标分析漏斗与留存。
- 访谈 5 至 8 名产生过有效计划的用户，以及 5 名生成后未执行的用户。
- 检查 AI 成本、失败类型、替换原因和清单未执行原因。
- 清理无效入口和低使用选项，不因已经开发而保留。
- 仅在达到下方准入条件后，立项下一阶段。

验收标准：

- 第 5 个工作日输出发布检查和初步复盘；发布后第 14 天补齐留存、有效计划率、用户原话和下一阶段选择。
- 下一阶段最多选择一个主方向，不能同时启动账户、旅行、电商和高级营养。

## 7. 事件与数据定义

建议最小事件集：

| 事件 | 触发时机 | 必要属性 |
| --- | --- | --- |
| `menu_page_viewed` | 打开菜单页 | 来源入口、是否首次用户 |
| `template_selected` | 选择首页模板 | 模板 ID |
| `generation_started` | 生成请求通过校验 | 天数、餐次、人数、场景、任务 ID |
| `generation_completed` | 得到结果 | source、耗时、warning 数、菜品数 |
| `generation_failed` | 生成不可用 | 错误类型、阶段、是否重试 |
| `meal_replaced` | 替换成功 | 日期、餐次、替换粒度、原因 |
| `menu_saved` | 保存成功 | 是否编辑过、替换次数 |
| `recipe_viewed` | 打开菜品详情 | 菜品 ID、入口 |
| `shopping_list_viewed` | 得到清单 | 菜单 ID、日期范围、条目数 |
| `shopping_item_updated` | 勾选或标为已有 | 状态、分类；不记录自由文本名称 |
| `shopping_list_exported` | 复制、分享或导出 | 格式 |
| `dish_feedback_submitted` | 提交轻反馈 | 反馈枚举、来源菜单 |
| `next_plan_started` | 从历史计划启动下一周期 | 来源菜单 ID、复制或重新生成 |

数据规则：

- 事件属性只接受服务端白名单字段。
- API Key、Base URL、完整 Prompt、完整 AI 输出、具体忌口自由文本不得进入分析事件。
- `client_id` 只用于匿名产品分析和数据隔离；引入账号后建立明确的迁移与删除机制。
- 报表必须把 `ai`、`repaired`、`sample` 和 `cache` 分开，不能把样例兜底当作 AI 成功。

## 8. 可直接进入开发看板的任务

## 9. 每项功能的完成标准

所有任务必须同时满足：

- 正常、加载、空、失败、重试和无 Supabase 降级状态均有明确行为。
- 新旧菜单结构都可读取；数据结构修改有 migration 和降级写入。
- API 输入使用 Zod 校验，AI 输出使用结构化 schema 校验。
- 不把 service role key 或浏览器本地模型配置写入客户端日志、数据库事件或 Supabase 业务表。
- 桌面宽屏和移动端完成关键流程检查，表格与按钮无不可控溢出或文字遮挡。
- `pnpm lint` 与 `pnpm build` 通过。
- 核心领域逻辑有自动化测试；高风险主流程至少有一条端到端冒烟测试。
- 上线后有对应事件或运行日志，可以判断功能是否被使用、是否成功。

## 10. 暂不做清单

本轮一周冲刺明确不做：

- 旅行路线、实时餐厅推荐和地图接入。
- 外卖平台、自动下单和生鲜电商购物车。
- 家庭邀请、多人权限与协同编辑。
- 订阅付费、套餐和广告。
- 医疗级营养建议、疾病食谱和微量营养精确承诺。
- 多语言、社区内容流和公开食谱社交。
- 复杂库存、保质期和价格预测。
- 独立微服务、向量数据库和复杂推荐基础设施。

已有旅行、外卖和节日 Prompt 可以保留为实验入口，但不继续投入外部数据、独立页面或商业合作。

## 11. 后续方向的准入条件

### 账户与跨设备

满足以下任一条件再启动 Supabase Auth：

- 次周回访率 >= 20%，且至少 30% 的回访用户有跨设备需求；
- 个人食谱、反馈或采购状态丢失成为前五位用户投诉；
- 开始提供付费能力，必须建立可靠的数据归属和删除机制。

### 权威营养数据库

同时满足以下条件再投入：

- 健康目标用户占有效计划用户 >= 30%；
- 营养详情打开率 >= 40%；
- “估算不可信”进入前三位流失或替换原因。

先接可靠食物营养数据并做本地计算，再增加维生素和矿物质字段。

### 采购平台

同时满足以下条件再评估一个平台试点：

- 采购清单打开率 >= 50%；
- 清单执行动作率 >= 65%；
- 食材标准化匹配率 >= 90%；
- 明确获得平台接口、联盟链接或合规跳转方案。

### 家庭共享

同时满足以下条件再立项：

- 有效计划用户中，至少 25% 主动分享或导出清单；
- 用户访谈确认共享的核心任务是分工采购或共同选菜，而不是单纯发图片；
- 已有账号、数据归属和冲突处理方案。

### 旅行与外食

只有家庭场景次周回访率稳定达到 20%，且连续 4 周增长停滞时，才用单独实验验证。该实验必须有可靠的地点/商家数据源，不能只依赖模型常识输出实时推荐。

## 12. AI 辅助开发节奏

- 每天开始：把当天目标拆成接口、数据、UI、测试四类验收项，让 AI 分批实现，避免一次生成大范围改动。
- 每个功能完成：立即运行 lint、build、领域测试和浏览器冒烟检查，不把验证集中拖到最后一天。
- 每天下午：发布一个可回滚的小版本，查看漏斗、失败日志和真实反馈，再决定次日范围。
- 第 5 个工作日：完成整体验收和首轮发布；发布后第 7 天和第 14 天分别复盘一次产品指标。

AI 提高的是实现和修复速度，不会自动提高需求正确率。路线图按每日验收结果滚动调整，但北极星指标、护栏指标和“不做清单”不因临时想法随意变化。
