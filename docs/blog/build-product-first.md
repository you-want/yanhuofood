# 我做了一个 AI 菜单工具：先把产品做好，再考虑开源

每天到了饭点，总会遇到一个看起来很简单、实际上特别磨人的问题：今天吃什么？

一个人吃还好，随便对付一下也能过去。但只要变成两个人、三个人，甚至一家人，这件事马上就复杂了。

有人不吃辣，有人想减脂，有人最近胃不舒服；家里还有昨天剩下的青菜，冰箱里的肉再不吃就要坏了。好不容易把菜单想明白，下一步又是：要买什么？买多少？哪几样家里已经有了？

我做“烟火食间”，就是想把这些琐碎但每天都要面对的问题，尽量放进一个顺手的工具里。

在线体验：[https://www.yanhuofood.com](https://www.yanhuofood.com)

公开产品仓库：[https://github.com/you-want/yanhuofood](https://github.com/you-want/yanhuofood)

## 它不是只会吐出一张菜单

我一开始也觉得，AI 生成几个菜名应该不难。真正做下去才发现，生成菜单只是最前面那一步。

一张看着挺丰富的菜单，如果不管忌口、不管人数、不管做饭时间，也不考虑食材能不能复用，那它大概率只是“看起来不错”，真到了晚上还是不知道怎么做。

所以现在生成菜单前，可以先把这一次的实际情况说清楚：

![烟火食间菜单生成设置](../../assets/screenshots/menu-settings.png)

比如喜欢什么菜系、有没有忌口、想控制热量还是补充蛋白质、计划几天、每天吃几餐、几个人吃、能接受多长的烹饪时间。

这些条件不一定每次都一样。周末有空，可以做复杂一点；工作日回家晚，就应该尽量快手。旅行、外食和集中备菜，也不应该套用同一套逻辑。

## 菜单生成之后，事情才刚开始

现在的烟火食间会把菜单、菜品详情、营养估算、食材清单和历史记录串在一起。

![烟火食间生成后的周菜单](../../assets/screenshots/weekly-menu.png)

不喜欢某道菜，可以换掉；想自己改，也可以直接编辑。打开菜品详情能看食材和步骤，还能跳到抖音搜索相关做法。菜单确定后，食材会汇总成采购清单，买过了、家里已经有了，都可以标记。

我比较在意的一点是：这个工具最后要能落到生活里，而不是生成完一段文字就结束。

说白了，菜单再聪明，最后不能帮你少纠结十分钟、少漏买两样菜，那就还是不够好用。

## 为什么源码现在还不开？

这个问题我认真想过。

我自己也喜欢开源，也知道一个公开源码的项目更容易获得关注和信任。但烟火食间现在还在快速变化，很多功能、数据结构和交互都没有完全定型。

现阶段我更想把时间花在这些事情上：

- 菜单到底能不能稳定生成，而不是偶尔成功一次。
- 历史数据出问题时，用户之前的菜单会不会丢。
- 手机上能不能顺手操作，按钮会不会挤成一团。
- 换菜以后，采购清单会不会跟着正确变化。
- 用户填过的偏好和模型配置，应该放在哪里才合适。

开源不是把仓库从 Private 改成 Public 就结束了。真正负责任的开源，还要补文档、整理架构、处理安全边界、回答问题、维护贡献流程。

如果现在一边高速改产品，一边为了让临时实现看起来“适合开源”而花很多时间包装，我担心最后两边都做不好。

所以当前的选择很直接：源码先保持私有，先认真把产品做好。

这不是说以后一定不开源，也不是拿“闭源”当什么神秘护城河。等产品边界更稳定、哪些部分适合开放更清楚以后，我愿意逐步开放一些通用的数据格式、工具模块，甚至重新评估更大范围的开源。

但我不想现在就画一个日期出来。先把事情做好，再谈承诺。

## 那为什么还要建一个公开 GitHub 仓库？

虽然源码暂时不公开，但产品进展、路线图和问题反馈没有必要关在私有仓库里。

所以我建了这个公开仓库，用来放：

- 产品介绍和真实截图
- 更新记录
- 产品路线图
- Bug 和功能建议入口
- 后续关于开源计划的变化

如果你觉得这个方向有点意思，可以去仓库点一个 Star。它不仅是一个数字，也能让我知道：确实有人也被“今天吃什么、明天买什么”这件事折腾过。

GitHub：[https://github.com/you-want/yanhuofood](https://github.com/you-want/yanhuofood)

产品体验：[https://www.yanhuofood.com](https://www.yanhuofood.com)

如果你实际用过以后发现哪里不好用，也欢迎直接提 Issue。比起一句“挺好的”，一个具体的生活场景往往更有价值。

比如：家里有老人和孩子，忌口不一样；工作日只有二十分钟做饭；想一次买完五天的菜，但又不想天天吃重复的。

这些真实问题，才是我接下来最想继续解决的东西。
